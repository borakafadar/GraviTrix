# GraviTrix agent instructions

## Run and verify

- Use Unity **6000.4.3f1**, pinned in `ProjectSettings/ProjectVersion.txt`. Open this root as the Unity project; the generated C# solution is not a standalone application.
- On a fresh clone, run `git lfs pull` before importing in Unity: sprites, fonts, and audio are LFS-managed.
- Default verification for gameplay/UI changes: let Unity compile, check the Console, then enter Play Mode in `Assets/Scenes/HomeScene.unity` and follow **PLAY -> MainScene**. Exercise the affected controls, rotation, pause/restart, or game-over flow. EditMode tests live in `Assets/Editor/Tests/` (namespace `GraviTrix.Tests`). They compile into `Assembly-CSharp-Editor` so they can see the game code, which has no assembly definitions. Run them from Window > General > Test Runner, or through the CLI with `unity command run_tests -- --mode EditMode --filter GraviTrix.Tests`. There is no CI or lint/build wrapper. Both scenes contain the `AudioManagers` prefab, so audio works when starting Play Mode from either scene.
- Keyboard smoke-test shortcuts: A/D or left/right arrows move; Q/E rotate left/right (W/up also rotates left); S/down soft-drops; **Enter hard-drops**; **C, left Shift, or Space holds**; R restarts at any time; Esc (Android Back) toggles pause.
- The `com.unity.pipeline` package in `Packages/manifest.json` lets the `unity` CLI drive an open Editor. Run `unity status` to find a connected Editor, `unity command` to list what it exposes, and `unity command eval` to run C#. With an Editor open, prefer this over hand-editing `.unity`/`.prefab`/`.asset` YAML. If `unity status` finds nothing, check whether Unity is actually running before editing files directly. `eval` gives up after 5 s on Unity's main thread; pass `-- --code '...' --timeout 15000` for heavier work. When the Unity window is in the background, Play Mode freezes until `Application.runInBackground` is set to true (the project value is false, so restore it afterwards). `capture_game_view --save_path` is relative to `Assets/` and rejects `..`, so delete the capture afterwards or it gets imported as an asset. While Unity is in the background, `--source screen` can return a stale or ghosted Game view; use `--source camera` to check UI state.
- Compiler warnings are in `%LOCALAPPDATA%\Unity\Editor\Editor.log` (known: CS0618 for `FindObjectOfType`, CS0162 in `GameController.TryCreatePieceFromLibrary`). `Core/*.cs` can also be smoke-tested outside Unity by compiling it with the .NET SDK against a small `UnityEngine` stub (`Vector2Int`, `Mathf`, `Random`, `Time`, `MonoBehaviour`/`ScriptableObject`, attributes) plus recording stubs for `BoardView`, `GameHudView`, `GameOverPopup`, and `SfxManager`.
- Supported targets are Android, Windows, desktop Web, and mobile Web. Use `File > Build Profiles` and the assets under `Assets/Settings/Build Profiles/`. All profiles inherit the global scene list: HomeScene, then MainScene. A disabled `SampleScene` entry points to a missing file. Web profiles have their own serialized Player Settings overrides, so inspect the selected profile when changing build settings. The Android profile has no overrides, so global Player Settings apply, including auto-rotation with landscape allowed. Web - Desktop ships Brotli without a decompression fallback.

## Runtime wiring and gameplay traps

- Scripts compile into one `Assembly-CSharp` assembly. `Assets/Scripts/GraviTrix/Core/GameController.cs` owns the phase/state loop and calls the Runtime views and UI directly; `Core` is not an isolated Unity-free library.
- Board coordinates use **+y downward**; `BoardView` negates y for rendering. `GameController` hard-codes a **12x12** board, ignoring `GameConfig.BoardWidth/BoardHeight`.
- Board rotation alternates left 90 degrees and right 90 degrees back to the original state. There is no active piece during rotation; animation completion callbacks advance rotation/settling phases. Preserve that callback chain when editing `BoardView` animations.
- `RestartGame()` first calls `BoardView.ResetView()`. It stops every `BoardView` coroutine, so pending callbacks (rotation -> drop -> slippery slide -> spawn, game over -> popup) never fire, and restores BoardRoot's transform and the grid colour saved in `Awake`. It also destroys every tracked view through `ClearViews()`, including the HOLD/NEXT preview pieces under the `PreviewAnchor`s, and then everything else under BoardRoot except the grid. Never clear `spawnedViews` without destroying its objects: anything dropped from the list is never cleaned up. Any new animation that changes BoardRoot, the grid or other scene objects must be undone there too. The high score is saved in `TriggerGameOver` (`GameOverPopup.SaveHighScore`), not when the popup appears, so a run counts even if the player restarts during the game-over animation. To test timing-sensitive flows through the CLI, trigger the second step inside Unity (for example from an `EditorApplication.update` callback that checks `Time.time`): each `eval` call compiles first and takes 1–2 s, which is longer than these animations. Pause is `Time.timeScale = 0`. `GameInputRelay` sends every keyboard, touch and mobile-button action through its `Active` property, which returns null while `timeScale` is 0, so nothing reaches `GameController` while paused. Any new input path must go through `Active` too. `PauseGame` refuses to pause during `GamePhase.GameOver` (Esc or the pause button). `RestartGame()` still resets `timeScale` to 1 without telling `PauseMenuView`; the pause menu's RESTART resumes first, so keep it that way. To test keys through the CLI, queue `KeyboardState` events with `InputSystem.QueueStateEvent` from an `EditorApplication.update` callback: press on one frame, release a couple of frames later.
- Rendering: `BoardView.Render` rebuilds every cell view, so keep the number of calls low. `SpawnNextPiece()` renders on success, and `TriggerGameOver` renders on failure, so don't call `RefreshViews()` after it. A hard drop moves the piece without rendering (`TryAdvancePiece(..., render: false)`) and relies on the lock path to render once; `BeginBoardRotation` renders the locked piece before the board turns. A failed rotation renders nothing.
- After rotation, settling drops the whole arrangement as one rigid group; only `Slippery` cells then fall individually, and only after a rotation. Lava clears the cells under it before every downward move, so it always reaches the floor and converts to Normal/Obsidian through `BoardGrid.LastExtinguished`, a read-only view of the last extinguish pass. `Clear()` and `ClearAll()` reset it, and so does a rotation, because both rotate methods call `Clear()`. Metal adjacency is checked after a lock and after rotation/slide, not after row-clear compaction.
- Live spawning uses `FallbackPieceFactory`. The serialized `PieceLibrary` is currently bypassed, and `TryCreatePieceFromLibrary` returns false immediately. Editing `PieceDefinition` assets alone will not change spawned shapes. Special-piece odds and `CreateLava`/`CreateMetal` depend on template array indexes. Templates carry a `Rotatable` flag; the O and lava 2x2 pieces are not rotatable, because their corner pivot would only shift them. `PieceInstance.TryRotate` tries kicks in this order: (0,0), (-1,0), (+1,0), (0,+1), (0,+2). The downward kicks let every piece rotate on the spawn row (the I piece needs two rows). There are deliberately no upward kicks, so rotating can never lift a piece or stall its fall. `Assets/Editor/Tests/PieceRotationTests.cs` covers these rules.
- MainScene's UI is authored in the scene. The HUD Canvas (under `GameRoot/Canvas/HUD`) is Screen Space - Camera on the Main Camera, with its scaler set to 1080x1920 and match 0.5. The score text, progress bar and rotation arrow are laid out there, so edit them in the Inspector. `GameHudView` only updates values: score text, bar fill and colour, arrow flip, and tick marks spawned from `Assets/Prefabs/HudTick.prefab`. It also spawns `ComboText`/`ActionText` prefabs with raycast target off. The pause button and pause popup are authored under `GameRoot` ("PauseButton Canvas" and "PauseMenu Canvas", inactive by default). `PauseMenuView` only toggles them, and its buttons and sliders call it through persistent events. The Game Over popup is authored the same way as "GameOverPopup Canvas" (inactive) under the `GameOverPopup` object. `GameOverPopup` only fills in the score and record and wires RETRY/MAIN MENU. The popup appears when `BoardView`'s game-over animation finishes. The animation calls its completion callback even when there are no blocks to drop, so an empty-board game over still shows the popup. `GameController` null-checks every `boardView` call, so it also runs without views; `Assets/Editor/Tests/GameControllerTests.cs` drives it that way. Check their builders and lifecycle methods before changing scene Canvas layouts. Cameras enforce 9:16 via `AspectRatioEnforcer`; HUD/menu scaling uses 1080x1920. The enforcer only runs in Play Mode, so set the Game view to a portrait 1080x1920 resolution. With a landscape Game view, Edit Mode shows the UI stretched, and Play Mode squeezes it into a narrow strip where text looks blurry.
- Team direction: objects belong in the Editor, not in code. Author UI, cameras, EventSystems, popups, and effects as scene objects or prefabs, with sprites and clips assigned in the Inspector. Don't add new runtime `new GameObject`/`AddComponent`/`Texture2D.SetPixel` setup. Instantiating prefabs for dynamic content (block cells, effect instances) is fine. When editing a code-built system, prefer moving it into a scene or prefab.
- HomeScene is fully authored in the scene. It contains the camera (tagged MainCamera, with the menu's only AudioListener), the "Main Menu Canvas" with the Options popup, an EventSystem (`StandaloneInputModule`), and the `AudioManagers` prefab. `MainMenuBuilder` only holds behavior. Its buttons and sliders call its public methods through persistent events set in the Inspector, and `FlyingBlocksManager` spawns `Assets/Prefabs/FlyingBlock.prefab`. MainScene has its own EventSystem with `InputSystemUIInputModule`.
- The six mobile buttons are authored under the HUD Canvas as "MobileControls". Each button's OnClick calls the matching `GameInputRelay` method (`OnMoveLeft`, `OnSoftDrop`, `OnHoldPiece`, and so on), set in the Inspector. The Hold button has no artwork yet: it shows a dark box with "Hold" text, so assign a sprite to its Image when one exists. The plain "Canvas" Transform under `GameRoot` is only a parent for the HUD. `GameInputRelay` ignores a touch that starts or ends over a UI raycast target, so a button tap never also counts as a board tap-to-rotate. The press check only works because uGUI's `EventSystem` updates first (its execution order is -1000, from the package). The release check holds even if that order changes, because `InputSystemUIInputModule` keeps a touch's pointer for one frame after release. To test touch in the Editor, add a virtual `Touchscreen` with `InputSystem.AddDevice`. Queue `TouchState` events (Began, then Ended a few frames later) at `RectTransformUtility.WorldToScreenPoint` of the target. For the test only, set `InputSystem.settings.editorInputBehaviorInPlayMode` to `AllDeviceInputAlwaysGoesToGameView` and `backgroundBehavior` to `IgnoreFocus`, otherwise an unfocused Game view drops the events. Afterwards, restore both settings and remove the device: devices added in Play Mode survive leaving it.

## Assets and Unity settings

- Gameplay ScriptableObjects live in **`Assets/Data/`**, not root `Data/`. Check serialized values and scene references alongside script defaults; `Assets/Data/GameConfig.asset` is already assigned in MainScene.
- Keep Active Input Handling set to **Both** (`activeInputHandler: 2`): `GameInputRelay` polls the new Input System, while HomeScene's EventSystem uses a legacy `StandaloneInputModule` and `MainMenuButtonEffect` reads `Input.mousePosition`.
- Block sprites, including Slippery's `block_removed` look, come from the BlockCellView prefab's skin library. No script uses `AssetDatabase` or `UNITY_EDITOR` sprite fallbacks, so the Editor shows what players see. Board effects are prefabs in `Assets/Prefabs/Effects/`, assigned on `BoardView`: `ClearShard` (line-clear shard sprite), `BombCloud` (explosion cloud sprite and colour) and `SmokeEffect` (lava-extinguish particles, which play on spawn and destroy themselves). Tune their look in the prefabs. Motion, timing and the board shake stay in `BoardView`'s coroutines. The explosion shards and lava melt pieces still copy the affected cell's sprite through `cellPrefab`. During a hard drop, `GameController` collects lava melts and plays one melt effect and one sound afterwards.
- The board layout is authored in MainScene. `BoardView.cellSize` (0.3611111) and `boardOffset` (the local position of the top-left cell) are serialized values matching the 9:16 camera at orthographic size 5. The grid (`BoardRoot/BackgroundGrid`: a tinted `white.png` quad plus the `Assets/Art/UI/grid_lines.png` sprite, imported at 100 px per cell) and the `HoldBox`/`NextBox` (border, inner, TMP label, `PreviewAnchor`) are scene objects laid out for those values. If you change the camera size or `cellSize`, move or rescale them too. `BoardView` only spawns cells (from `Assets/Prefabs/BlockCellView 1.prefab`) and the half-scale preview pieces under each `PreviewAnchor`. The camera colour and `AspectRatioEnforcer` are set on the scene camera. Cell views are never scaled to `cellSize`: block size on screen comes from sprite import PPU (2000 for the ~726 px slices).
- `Assets/Data/GameConfig.asset` doesn't serialize `comboBonus` or `lavaMeltScore` (script defaults apply), and `BoardRotationPauseSeconds` is unused. Animation timings are constants in `BoardView`/`GameController`.
- `Assets/Art/UI/` holds the UI sprites (panels, buttons, slider parts, the menu grid, `white.png`). They are pixel-exact exports of the old runtime generators. HomeScene and the pause and game-over popups use them, and no runtime sprite generators remain. MonoBehaviours that are saved into scenes or prefabs need their own file named after the class, or they load as missing scripts.
- Audio lives on `Assets/Prefabs/AudioManagers.prefab`: one GameObject with `MusicManager` and `SfxManager`, each with its own AudioSource, and every clip from `Assets/Art/Music/` and `Assets/Art/Sound Effects/` assigned in the Inspector. The prefab sits in both scenes. The first one loaded marks itself `DontDestroyOnLoad`, and later copies destroy themselves. To add a sound, add an `AudioClip` field and assign it on the prefab. There is no `Resources` folder. The music clip streams from disk.
- Preserve existing `.meta` GUIDs when moving/renaming assets or scripts, and include metadata for new assets. Scene/prefab references depend on them. Keep code edits under `Assets/`; Unity regenerates `*.csproj`, and `Library/`, `Temp/`, `Logs/`, and `UserSettings/` are local/generated state.
